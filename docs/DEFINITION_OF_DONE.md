## 1. الهدف وفلسفة الجودة (Purpose & Core Principle)

يحدد هذا الميثاق **"الحد الأدنى الإلزامي للجودة"** الذي يجب أن تستوفيه أي مهمة برمجية، توثيقية، أو اختبارية قبل أن يُسمح بنقلها إلى عمود **`Done`** في الـ Project Board أو دمجها في الفرع الرئيسي `main`.

> [!IMPORTANT]
> **القاعدة الذهبية لفريق شيدرا (SHIDRA TEAM):**  
> *"المهمة لا تُعتبر منجزة بمجرد كتابة الكود، بل تكتمل فقط عندما تكون مختبرة، ومطابقة للتصميم، ومراجعة من زميل آخر، ومدمجة بأمان دون أخطاء."*

## 2. مستويات معايير الاكتمال (Multi-Level DoD Matrix)

### المستوى 1: معايير اكتمال وثائق التخطيط (Documentation DoD)
تنطبق هذه الشروط على جميع ملفات مجلد `docs/`:
- [ ] صياغة الوثيقة وفق تنسيق Markdown سليم ومزودة بجداول ورسوم بيانية توضيحية (Mermaid).
- [ ] خلو الوثيقة التام من المعلومات الوهمية أو التخمينية، مع استخدام وسم `[TO BE DEFINED]` للمعلومات غير المحسومة بعد.
- [ ] مزامنة الروابط التشعبية والتأكد من أنها قابلة للنقر وتعمل بشكل صحيح داخل المستودع.
- [ ] مراجعة الوثيقة من الزميل المعتمد ورفعها عبر Pull Request مخصص قبل اعتمادها.

---

### المستوى 2: معايير اكتمال الميزات البرمجية (Feature Development DoD)
تنطبق على كافة ميزات التطوير من `FR-01` إلى `FR-06`:
- [ ] **مطابقة المتطلبات:** الكود يحقق شروط القبول (Acceptance Criteria) المحددة في [`docs/SRS.md`](file:///e:/level_4/Software%20Engineering/Practical/Lab%201/docs/SRS.md).
- [ ] **احترام قواعد العمل الثلاث:**
  - `BR-01`: منع حجز أي فترة زمنية في الماضي أو سابقة للحظة الحالية.
  - `BR-02`: منع الحجز المزدوج لنفس الساعة عبر Database Transactions وقفل التزامن.
  - `BR-03`: منع اللاعب من إلغاء الحجز إذا تبقى أقل من ساعتين (120 دقيقة) على موعد المباراة.
- [ ] **الالتزام بنظام التصميم (Design System):**
  - استخدام درجات الألوان العشبية المعتمدة في [`docs/Design-System.md`](file:///e:/level_4/Software%20Engineering/Practical/Lab%201/docs/Design-System.md) (`#354C2B`, `#4E653D`, `#859864`, `#A4B17B`, `#C3CA92`).
  - التزام بالخطوط القياسية (Cairo / Tajawal للعربية و Inter للأرقام).
- [ ] **التجاوب الكامل (Responsive Web):**
  - عمل الواجهة بسلاسة على شاشات الجوال (Mobile 375px+) والمتصفحات المكتبية (`NFR-03`).
  - ألا يقل ارتفاع أزرار وخلايا الساعات عن `48px` لسهولة اللمس.
- [ ] **البرمجة الدفاعية ومعالجة الحالات الاستثنائية:**
  - التحقق الصارم من صحة المدخلات (Validation).
  - إظهار رسائل خطأ واضحة ومفهومة للمستخدم بدلاً من انهيار الصفحة.

### المستوى 3: معايير جودة الاختبارات (Testing & QA DoD)
تنطبق على جميع التعديلات البرمجية وفقاً لـ [`ai/rules/testing.md`](file:///e:/level_4/Software%20Engineering/Practical/Lab%201/ai/rules/testing.md):
- [ ] كتابة اختبارات آلية (Unit / Feature Tests) تغطي:
  - المسار الناجح الطبيعي (Happy Path).
  - المدخلات غير الصحيحة أو الفارغة (Invalid / Empty Input).
  - حالات الحافة وحدود قواعد العمل (Boundary Conditions).
- [ ] **مبدأ الصدق في الاختبار (Truth in Testing):** عدم ادعاء نجاح ميزة ما لم يتم تشغيل اختبارها فعلياً والتأكد من خلوها من الأخطاء.
- [ ] التأكد من عدم تسبب الكود الجديد في كسر أي ميزات سابقة في النظام (Zero Regression).

---

### المستوى 4: معايير الأمان والخصوصية (Security DoD)
- [ ] خلو الكود وملفات الـ Commits تماماً من أي كلمات مرور، مفاتيح API، أو ملفات `.env`.
- [ ] تشفير كلمات المرور باستخدام خوارزميات التشفير الآمنة (Bcrypt).
- [ ] حماية جميع النماذج من هجمات تزوير الطلبات عبر المواقع (CSRF Protection).
- [ ] تعقيم وتمرير جميع المدخلات لمنع هجمات حقن قواعد البيانات (SQL Injection) والـ XSS.

---

### المستوى 5: معايير الـ Git والمراجعة والدمج (Git & Peer Review DoD)
تنطبق على دورة حياة الكود وفقاً لـ [`ai/rules/git.md`](file:///e:/level_4/Software%20Engineering/Practical/Lab%201/ai/rules/git.md):
- [ ] إنشاء فرع مخصص ومسمى بدقة بحسب المعيار (`feature/*`, `docs/*`, `fix/*`).
- [ ] صياغة الـ Commits وفق أسلوب Conventional Commits (`feat:`, `fix:`, `docs:`, `test:`).
- [ ] فتح Pull Request واضح يرتبط بالـ Issue المعنية (`Closes #Issue`).
- [ ] **المراجعة الثنائية الإلزامية (Independent Peer Review):**
  - خضوع الـ PR لمراجعة دقيقة من الزميل المعتمد بحسب جدول المراجعات.
  - تطبيق وإصلاح كافة ملاحظات المراجعة (ممنوع منعاً باتاً أن يوافق العضو على كوده بنفسه).
- [ ] **صلاحية الدمج الحصرية:**
  - الدمج في `main` يتم حصرياً بواسطة الـ Repository Maintainer (محمد الإدريسي `@Mo-ra778`).
- [ ] إغلاق الـ Issue المعنية ونقل بطاقتها في الـ Project Board إلى عمود **`Done`**.

## 3. قائمة فحص الـ PR الجاهزة للنسخ (Pull Request DoD Checklist)

يُلزم كل مطور بنسخ هذه القائمة وإلصاقها في مربع وصف الـ Pull Request الخاص به قبل طلب المراجعة:

```markdown
### 📋 Definition of Done Checklist:
- [ ] الكود يحقق متطلبات الـ Issue والـ SRS المحددة.
- [ ] الكود يحترم قواعد العمل (BR-01, BR-02, BR-03).
- [ ] الواجهة مطابقة لنظام التصميم ومتجاوبة على الموبايل والكمبيوتر.
- [ ] تم اختبار الكود والتأكد من سلامة التشغيل.
- [ ] لا توجد كلمات مرور أو بيانات حساسة في الكود.
- [ ] الـ Commit مسمى وفق أسلوب Conventional Commits.
- [ ] جاهز للمراجعة من الزميل المعتمد (Peer Review).
```
